# Radio Vault 0.34.0 Alpha 19 Buildfix 6

Buildfix 5 confirmed that the phone could open and audibly decode the selected recording, but revealed that seeking was dependent on the recording itself. Some long MP3 files tell iPhone Safari that a seek succeeded while their decoder silently remains at the beginning. Radio Vault then correctly refused to commit the wrong playhead.

Buildfix 6 removes that file-dependent decoding and seek behaviour from the critical iPhone path. The server exposes a fresh, range-capable PCM stream, opening the source at the requested point when resuming or handing off. Radio Vault Web tracks that offset separately, so shared progress and multipart timing remain accurate. This same compatible representation is used when an iPhone starts at zero, preventing playback from varying with the original recording's codec details.

The fallback is lossless decoding rather than a lower-bitrate transcode. It uses more local network bandwidth while active, but it avoids another quality reduction and works independently of MP3 seek-table quality. Backwards seeking opens another positioned stream from the new point.

Install the Buildfix 6 server first, fully close Radio Vault Web on the phone, reopen it and confirm Buildfix 6. Test both a broadcast that starts at zero and one with saved progress. Then install the matching desktop client so connected capability generation 28 remains aligned.
