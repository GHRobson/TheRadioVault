# Beta 1 buildfix 1 — listening progress persistence

## Report that triggered the buildfix

A currently listened-to Bennington broadcast dated 16 July 2015 reappeared as **Unplayed · 0%** after recent launch/build changes. The supplied diagnostic was generated by `0.28.0-beta1`, schema 45, and reported no missing or cloud-only media. Its format exposed playback only for issue/sample rows, so it did not contain the affected broadcast's playback-state row; diagnostic format 6 now adds the 100 most recent playback records whenever playback details are selected.

## Failure boundaries addressed

- A transient zero position from media opening, closing, resume settling, browser heartbeat or output transfer could overwrite a positive SQLite position.
- Canonical playback was displayed across all member episode rows but routine progress writes targeted only one representative row. A later representative/member change could therefore make valid progress appear absent.
- Normal shutdown reused the guarded periodic-save path and could skip the final save while media was loading or a long database operation was active.
- A crash or blocked SQLite writer had no separate last-known-position recovery record.

## Buildfix contract

- Read playback state across every episode row belonging to the canonical broadcast.
- Write each accepted position to every retained member row so progress follows the canonical broadcast rather than one legacy episode ID.
- Refuse an implicit zero overwrite when positive progress already exists. Only the explicit **Mark unplayed** path may reset to zero, and that reset is applied to every retained canonical member.
- Force a final save during normal window closure.
- Write the active positive position to an atomic `playback-recovery.json` journal before each SQLite save.
- On startup, restore a newer journal entry only when the database has genuinely lost progress. Resolution tries the episode ID, canonical key and stable broadcast UID.
- Keep backward seeking to a non-zero position valid.
- Preserve schema 45; this is a persistence correction, not a database migration.

## Diagnostic improvement

Archive Health diagnostics with **Include playback** now contain a `recentPlayback` section with episode ID, canonical key, stable broadcast UID, show, date, title, position, duration, completion, speed and last-played timestamp. This makes a future report sufficient to inspect the affected state directly.
