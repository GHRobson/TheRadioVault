# Radio Vault 0.34.0 Alpha 19 Buildfix 2

This release repairs the canonical server audio stream used by both ordinary Radio Vault Web playback and cross-device handoff.

## What the diagnostic proved

The iPhone successfully loaded the MP3 metadata and initially reported its complete duration. When Radio Vault immediately applied the saved position, Safari discarded the fresh decoder, changed its duration to zero and ended. Because normal Library playback and handoff use the same canonical media endpoint and resume logic, this was not limited to ownership transfer.

## Canonical range-response repair

Safari obtains MP3 metadata, playback data and seek data through successive HTTP byte ranges. Canonical media responses now include a strong resource validator, last-modified date, private short-lived caching and `Vary: Range`. This lets Safari identify those partial responses as parts of the same unchanged recording while keeping the authenticated media private to the device.

The server continues to return exact `206 Partial Content`, `Content-Range`, `Content-Length`, `Accept-Ranges: bytes` and identity-encoding headers.

## iPhone decoder sequencing

On iPhone, Radio Vault now waits until a newly started muted decoder has advanced its real playback clock before applying a resume or handoff position. A metadata-ready decoder is no longer considered safe to seek. Ownership remains with the original device until the target stays aligned and the transactional commit succeeds.

## Upgrade and test

Install the Buildfix 2 server first. Fully close and reopen Radio Vault Web so Safari installs shell cache v48. First play a broadcast directly from the phone Library, then try a laptop-to-phone handoff. Install the matching client build afterwards to keep the connected capability generation aligned.
