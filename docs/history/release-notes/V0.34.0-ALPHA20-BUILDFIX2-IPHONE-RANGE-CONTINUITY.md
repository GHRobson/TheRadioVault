# Radio Vault 0.34.0-alpha20-buildfix2

## Outcome

Long-running iPhone playback now uses one continuous decoded PCM timeline even when Safari retrieves the positioned WAV representation in many HTTP byte ranges. Range boundaries can no longer introduce small forward skips or repeated audio.

## Root cause

The positioned WAV route previously reopened the compressed recording and sought Media Foundation independently for every byte-range request. Compressed decoder seeks are approximate, so the PCM generated for a later range could begin slightly before or after the matching point in a continuous decode. Safari joined those individually valid ranges into one media timeline, exposing the mismatch as periodic skips that changed direction over time.

## Correction

- Every `streamSession` owns a serialized positioned-wave decoder.
- Sequential ranges continue from that decoder rather than reopening and reseeking the source.
- A backwards or retried range safely resets the same session to its canonical starting point.
- Sessions are bounded, idle-expired and disposed with the Web server.
- Audio remains PCM WAV; no bitrate or quality reduction is introduced.

## Automated proof

The regression creates a changing-frequency WAV, encodes it to MP3, requests a positioned PCM response continuously, then reconstructs the same response from consecutive 32 KB ranges. The complete SHA-256 values must match exactly.

## Acceptance

1. Install the matching Server and Client builds and reopen Radio Vault Web on the iPhone.
2. Start or move a broadcast to the iPhone.
3. Listen continuously for at least 20 minutes.
4. Confirm speech and music remain continuous without small periodic jumps or repeated fragments.
5. Seek forward, continue listening, then complete two client → iPhone → client → iPhone handoff cycles without refreshing the Web page.
