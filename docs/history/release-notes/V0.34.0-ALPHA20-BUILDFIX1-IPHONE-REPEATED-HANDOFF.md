# Radio Vault 0.34.0-alpha20-buildfix1

## Outcome

Repeated iPhone handoffs no longer become trapped behind Radio Vault Web's dormant-decoder preparation spinner. iOS now performs the decoder replacement and proof inside the listener's Move tap, while non-iOS browsers retain background target preparation.

## Evidence behind the fix

The monitored reproduction completed client → iPhone at generation 13 and iPhone → client at generation 14. The next iPhone tap displayed a permanent spinner but produced no transfer ticket, generation change or pending server transfer. Refreshing the page allowed generation 15, and the same failure returned after generation 16. This isolated the fault to the iPhone-only Web control gate rather than the server transaction or playback engine.

## Regression contract

- iOS exits dormant decoder preparation before it can touch the shared audio element.
- Session polling does not start dormant preparation on iOS.
- Neither compact nor full-player Move controls are disabled by dormant preparation on iOS.
- The direct tap continues to create the positioned Safari decoder before awaiting the transfer ticket.
- The Web shell cache advances to v56.

## Acceptance

1. Install the matching client and server builds and open Radio Vault Web on an iPhone.
2. Start a broadcast in the native client.
3. Move playback to the iPhone and confirm audible, advancing playback.
4. Move playback back to the native client.
5. Without refreshing Radio Vault Web, confirm **Move to this device** is immediately available rather than showing a preparation spinner.
6. Move playback to the iPhone again and repeat the round trip twice.
7. Confirm each move preserves the broadcast/playhead, silences the previous output and leaves no pending server transfer.
