# Radio Vault v0.30.0 RC1 acceptance checklist

Target: `0.30.0-rc1-multi-device-release-candidate`

Use the real authoritative desktop library and at least one paired Windows remote client. Preserve the accepted Beta 1 installation until RC1 has passed the upgrade checks.

## 1. Build and package gate

- [ ] Extract RC1 to a fresh short path and build the full solution in Release.
- [ ] Run `release-gate.ps1`; source validation, compilation, regression/capability tests and assembly-version verification all pass.
- [ ] Run `package-release.ps1`; the `win-x64` ZIP, `BUILD_INFO.json` and SHA-256 file are produced.
- [ ] Extract the generated binary ZIP into another clean folder and launch it successfully.
- [ ] About/diagnostics, server discovery and copied parity diagnostics report `0.30.0-rc1-multi-device-release-candidate`.

## 2. Existing-install upgrade safety

- [ ] Launch RC1 over the accepted Beta 1 application/data locations on the server.
- [ ] Database schema remains 45 and canonical broadcast/recording counts are unchanged before any new scan.
- [ ] Existing library folders, Settings, secure certificate, paired clients, playback state, favourites, queue, Moments and Research remain present.
- [ ] Upgrade the remote client without clearing its cache or pairing information.
- [ ] The saved server reconnects normally; no re-pairing or cache reset is requested.

## 3. Clean-launch and local-library regression

- [ ] Launch RC1 with `--local-library` from a clean extraction.
- [ ] Dashboard, canonical Library, Explore, global search, Broadcast Info and Metadata Studio load normally.
- [ ] Play a single-file and multipart broadcast; seek, pause, resume, change speed and cross a part boundary.
- [ ] Confirm progress, favourites, queue, Moments and transcript jumps survive restart.
- [ ] Run a normal rescan and confirm the canonical Library remains correct and responsive.

## 4. Remote-client parity

- [ ] Run the same RC1 build on server and remote client.
- [ ] Refresh **Remote-client parity**; every published surface reports available.
- [ ] Compare Dashboard counts, Library rows/facets, Broadcast Info, artwork, transcript summary and Research overview with the server.
- [ ] Find a Research record through global search and open it in the normal Research workspace.
- [ ] Make one remote Metadata Studio edit and verify it appears on the server.
- [ ] Change favourite, listening status and queue remotely and verify write-through once, without duplication.
- [ ] Server-owned Research repair/reconciliation/rollback and artwork-file operations remain clearly blocked remotely.

## 5. Synchronization and outage recovery

- [ ] During remote playback, allow several routine progress saves and confirm the UI remains responsive.
- [ ] Copied parity diagnostics show incremental/no-change modes, bounded duration and zero persistent failures during healthy use.
- [ ] Stop the server while browsing; cached Library, Moments and transcript summaries remain readable and mutations are clearly blocked.
- [ ] Restart the server; bounded retry reconnects automatically and the live state replaces cached state without losing the active page/search/filter.
- [ ] Add or remove a test broadcast on the server and confirm the remote client performs a safe full reset when required.

## 6. Mode switching

- [ ] Switch local library → paired server and leave the replacement window open for at least 20 seconds.
- [ ] Switch paired server → local library and leave the replacement window open for at least 20 seconds.
- [ ] Repeat both directions twice; only one main window remains and no false unclean-session warning appears.
- [ ] After returning local, Connected Access still reports the local web server running.

## 7. Repeated shutdown

Perform at least three exits in each state:

- [ ] idle local-library/server mode;
- [ ] local playback active;
- [ ] idle remote-client live mode;
- [ ] remote playback active;
- [ ] remote client cached/disconnected;
- [ ] remote client reconnecting.

For every exit:

- [ ] the window closes normally;
- [ ] the process disappears from Task Manager within 12 seconds;
- [ ] the next ordinary launch does not report an unclean prior session;
- [ ] listening progress and queue/favourite state remain correct.

## 8. Daily-driver soak and release decision

- [ ] Use RC1 for at least one extended normal listening session involving playback, browsing, search, queue, Metadata Studio and Research.
- [ ] Leave server and remote client connected for several hours; responsiveness, memory use and connection state remain stable.
- [ ] Export diagnostics from both operating modes and confirm no credentials, tokens or archive audio are included.
- [ ] No operation writes to the remote client's dormant local database.
- [ ] No data loss, duplicate mutation, indefinite shutdown, stale-cache lockout or unexplained full-Library churn occurs.

RC1 is accepted when every applicable check passes. The next build should then be `0.30.0` stable; RC2 is only warranted for a reproduced release blocker.
