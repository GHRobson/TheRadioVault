# v0.30.0 Alpha 1 Buildfix 2 — remote-client pairing transport

## Fault isolated

Buildfix 1 proved that server and remote client discovery worked in both directions, but the server rejected the subsequent HTTPS pairing POST with HTTP 400. The client used `PostAsJsonAsync`, whose JSON content can be transmitted with `Transfer-Encoding: chunked`. Radio Vault's deliberately small built-in HTTP parser previously read only `Content-Length` request bodies, so it treated a valid chunked pairing body as empty.

## Repair

- The Radio Vault remote client now serialises `WebDesktopPairingRequest` into a bounded UTF-8 byte array and sends `ByteArrayContent`, producing an explicit `Content-Length`.
- The server now decodes standards-compliant HTTP/1.1 chunked bodies, including chunk extensions and trailers, while preserving the existing 16 KiB body limit.
- Every pairing failure now returns the versioned JSON pairing envelope, allowing the client UI to display the exact validation or recovery message.
- The client forces HTTP/1.1-or-lower for this small custom listener and disables `Expect: 100-continue`.

## Safety

The pairing code remains six digits, one-use, five-minute expiry and attempt-limited. Certificate pinning and token generation are unchanged. No database migration, web-shell cache change, IndexedDB change or media-cache invalidation is introduced.

## Acceptance

Build and install the same Buildfix 2 source on the server and remote client. Create a fresh pairing code on the server, rediscover it from the remote client, pair, and verify that the trusted bootstrap displays the server's canonical broadcast and show counts. Restart both apps and use **Test saved connection** to verify persistent trust.
